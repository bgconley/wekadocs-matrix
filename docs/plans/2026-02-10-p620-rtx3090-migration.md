# WekaDocs-Matrix P620 + RTX 3090 Migration Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Port the entire WekaDocs-Matrix application from macOS (Apple Silicon / MPS) to an AMD Threadripper P620 running Ubuntu 24.04.3 with an RTX 3090, consolidating all GPU inference services onto CUDA and leveraging the Threadripper's cores for database workloads.

**Architecture:** The app is a RAG pipeline with 3 databases (Neo4j, Qdrant, Redis), 3 Python app services, and 6 GPU-dependent ML services—all loosely coupled via HTTP REST. The migration strategy is: (1) install NVIDIA + Docker GPU prerequisites on the P620, (2) containerize all GPU services with CUDA support, (3) reconfigure networking so containers reach each other directly instead of via `host.docker.internal`, (4) tune resource limits for 24 Threadripper cores + 24GB VRAM, and (5) validate end-to-end with health checks and integration tests.

**Tech Stack:** Docker Compose with NVIDIA Container Toolkit, CUDA 12.x, PyTorch (CUDA), Triton Inference Server, Ubuntu 24.04.3, RTX 3090 (24GB VRAM)

## Phase 2: GPU Service Containerization

### Overview

Currently, the GPU services (BGE-M3, GLiNER, Qwen3 Reranker) run as native processes on the macOS host. On the P620, we'll containerize them with CUDA support and add them to the docker-compose stack. The Triton server (Qwen3-Embedding-4B) is already at `10.25.0.50:8200`—we'll decide whether to keep it remote or bring it local.

### Task 2.1: Create GLiNER CPU Dockerfile

**Files:**
- Create: `docker/gliner-ner.Dockerfile`

**Why:** GLiNER is used exclusively during ingestion (batch NER extraction), never at query time. On a 24+ core Threadripper, CPU inference for this ~400M parameter model is totally viable — and it frees ~2.3GB of GPU VRAM that we need for the Qwen3-Embedding-4B Triton server (see Task 2.5). The `device=auto` detection in `services/gliner-ner/server.py` will select CPU automatically since no GPU is exposed to this container.

**Latency tradeoff:** CPU will be ~3-5x slower than CUDA for GLiNER, but ingestion is a background batch process. The Threadripper's multi-core performance and high memory bandwidth partially compensate.

**Step 1: Create the Dockerfile**

```dockerfile
# docker/gliner-ner.Dockerfile
# GLiNER NER Service — CPU-only (GPU VRAM reserved for embedder/reranker)
# Rationale: GLiNER only runs during ingestion (not query time).
# On Threadripper PRO, CPU inference is sufficient for batch NER.
FROM python:3.11-slim

WORKDIR /app

# System deps
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    && rm -rf /var/lib/apt/lists/*

# Install CPU-only PyTorch first (smaller image, no CUDA overhead)
RUN pip install --no-cache-dir \
    torch --index-url https://download.pytorch.org/whl/cpu

# Python deps (gliner, fastapi, etc.)
COPY services/gliner-ner/requirements.txt /app/requirements.txt
RUN pip install --no-cache-dir -r requirements.txt

# Copy service code
COPY services/gliner-ner/server.py /app/server.py

# Pre-download model during build (avoids runtime download)
RUN python -c "from gliner import GLiNER; GLiNER.from_pretrained('urchade/gliner_medium-v2.1')"

# Non-root user
RUN useradd -m -u 1000 appuser && chown -R appuser:appuser /app
USER appuser

EXPOSE 9002

HEALTHCHECK --interval=10s --timeout=5s --retries=3 --start-period=60s \
    CMD curl -f http://localhost:9002/healthz || exit 1

# device=auto will select CPU since no CUDA is available in this container
CMD ["python", "server.py", "--device", "cpu", "--port", "9002"]
```

> **Note:** We explicitly pass `--device cpu` and use `python:3.11-slim` (not the CUDA PyTorch image). This makes the image ~3GB smaller and avoids wasting GPU memory. The `services/gliner-ner/server.py` already handles CPU inference — no code changes needed.

**Step 2: Verify it builds (on P620)**

**Step 3: Smoke test**

### Task 2.4: Bring Triton + Qwen3-Embedding-4B Local

**Decision: BRING IT LOCAL.** By moving GLiNER to CPU (Task 2.1), we freed ~2.3GB of GPU VRAM. The revised VRAM budget is:

| Service | VRAM |
|---------|------|
| BGE-M3 | ~2,500 MiB |
| Qwen3-Reranker-4B | ~8,000 MiB |
| Qwen3-Embedding-4B (Triton) | ~8,000 MiB |
| CUDA context overhead (×3 procs) | ~2,100 MiB |
| **Total** | **~20,600 MiB (~84%)** |
| **Headroom** | **~4,000 MiB** |

2. The FastAPI gateway container (or collocated with Triton)

## Phase 3: Networking & Configuration Overhaul

### Task 3.1: Eliminate `host.docker.internal`

**Why:** On macOS, `host.docker.internal` is a magic DNS name that resolves to the host. On Linux, it's not available by default (Docker 20.10+ supports it with `extra_hosts` or `host-gateway`, but it's fragile). Since we're containerizing all GPU services, they should communicate over the Docker bridge network directly using container names.

**Files:**
- Modify: `docker-compose.yml`
- Modify: `.env.docker`
- Modify: `.env.example`

| `http://host.docker.internal:9002` | `GLINER_SERVICE_URL` | `http://gliner-ner:9002` |

### Task 4.2: NVIDIA GPU Sharing Configuration

**Why:** All three GPU services share a single RTX 3090. Docker Compose's `count: 1` + `capabilities: [gpu]` gives each container access to the same GPU. PyTorch handles VRAM allocation dynamically—containers don't pre-allocate fixed VRAM slices.

**Important: CUDA MPS (Multi-Process Service) consideration**

By default, GPU processes time-share the GPU (context switching). For better concurrent utilization, you can enable NVIDIA MPS:

```bash
# On the host:
sudo nvidia-smi -i 0 -c EXCLUSIVE_PROCESS  # Optional: exclusive mode
nvidia-cuda-mps-control -d                   # Start MPS daemon
```

**However**, MPS is primarily beneficial for HPC workloads with many small kernels. For inference services that hold the GPU for longer bursts, the default time-sharing is fine. **Recommendation: Skip MPS initially**, monitor with `nvidia-smi dmon` and add it if you see GPU utilization issues.

**Files:**
- Create: `/etc/docker/daemon.json` (on P620 host)

An alternative is to only specify the NVIDIA runtime in compose for GPU services (via `deploy.resources.reservations.devices`), which is what we do in Phase 3.2.

## Appendix A: VRAM Budget

RTX 3090 Total VRAM: **24,576 MiB (24 GB)**

### Final Architecture: GLiNER on CPU, everything else on GPU

The key insight: GLiNER is ingestion-only (never runs at query time), so it doesn't need GPU. Moving it to CPU frees VRAM for the Qwen3-Embedding-4B Triton server, enabling a fully self-contained single-machine deployment.

| Service | Model | VRAM | Runtime | Notes |
|---------|-------|------|---------|-------|
| BGE-M3 | BAAI/bge-m3 | ~2,500 MiB | PyTorch | Dense + sparse + ColBERT heads |
| Qwen3 Reranker | Qwen/Qwen3-Reranker-4B | ~8,000 MiB | PyTorch | Cross-encoder, query-time |
| Qwen3 Embedding | Qwen/Qwen3-Embedding-4B | ~8,000 MiB | Triton | Dense embeddings, ingest + query |
| GLiNER | urchade/gliner_medium-v2.1 | **0** | CPU | Ingestion-only batch NER |
| CUDA context overhead | (per GPU process) | ~700 MiB × 3 | — | BGE-M3 + Reranker (PyTorch) + Triton |
| **Total GPU** | | **~20,600 MiB** | | **~84% utilization** |
| **Headroom** | | **~4,000 MiB** | | Sufficient for inference spikes |

### Why ~4GB headroom is safe

Embedding and reranking don't spike simultaneously in normal operation:
- **During ingestion:** Embedding (Triton) is active, reranker is idle
- **During queries:** Reranker is active, embedding is active (for query vector), but single-request VRAM spikes are small
- **Batch inference spikes** (e.g., embedding 32 texts at once) increase GPU *compute* utilization, not VRAM — the model weights stay constant

The main risk is PyTorch CUDA memory fragmentation over long uptimes. Monitor with `nvidia-smi` and restart services if VRAM creeps above 22GB.

### VRAM Optimization Options (if headroom proves too tight)

| Technique | Savings | Tradeoff |
|-----------|---------|----------|
| INT8 quantization (bitsandbytes) | ~50% per model | Minor quality loss, need `bitsandbytes` dep |
| GPTQ/AWQ quantization | ~50-75% | Requires pre-quantized model weights |
| Triton TensorRT optimization | ~30-40% on Qwen3-Emb | Complex setup, model-specific |
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | Reduces fragmentation | Set as env var in compose |
