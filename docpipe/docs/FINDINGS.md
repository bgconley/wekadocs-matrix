## Details


### 1. [HIGH] A still-truncated bumped result is written as status=ok and cached forever, so an over-long page is silently frozen mid-content and never retried
- **Location:** `convert.py:181` · **Dimension:** concurrency · **Verdict:** confirmed
- **What:** Only the FIRST response's `.truncated` is checked (convert.py:181). The bumped second response is used unconditionally (convert.py:184) and passed to write_success with status='ok' (convert.py:189-193, artifacts.py:97-106). If that second response is ALSO finish_reason=='length' (page needs more tokens than the bumped ceiling), the truncated markdown — typically cut mid-table or mid-code-fence — is persisted as a successful artifact. is_done (artifacts.py:66-72) then returns True permanently, so every future `convert`/`retry-failed` run skips it. The truncated page is baked into the corpus with no signal and no recovery path. Truncation-written-as-ok is not among the CONTEXT known issues.
- **Failure scenario:** A dense CLI command-reference page needs ~15000 completion tokens. With default max_tokens=6000 the first call truncates; the bump retries at 9600; the second result is still finish_reason=='length' but is written via write_success as status='ok'. is_done returns True forever, so the page (cut off mid-table) is cached as complete and never re-attempted, permanently truncating that page in the output doc.
- **Suggested fix:** After the bump, if `result.truncated` is still true, treat the page as failed (write_failure or re-enqueue) rather than write_success, so it is retried / surfaced in QA. Optionally record a `truncated` flag in PageMeta so downstream QA can flag it.

### 2. [HIGH] demote_extra_h1s + balance_fences shatter fenced code blocks that contain '#' comments, dropping code fencing and injecting spurious headings
- **Location:** `clean.py:63` · **Dimension:** extraction-quality · **Verdict:** confirmed
- **What:** clean_document runs ensure_title_h1 -> demote_extra_h1s (clean.py:161) BEFORE balance_fences (clean.py:162), and both passes are code-fence-unaware. demote_extra_h1s (clean.py:57-69) rewrites every non-first '# ' line to '## ' by pure line matching (_ANY_H1_RE, clean.py:63) with no awareness of open code fences. Since ensure_title_h1 guarantees a title H1 is the first line, EVERY '#'-space comment inside a fenced bash/config block (ubiquitous in this CLI/nCLI/aCLI/config-heavy corpus: '# Create the network', '# Note: replace IP') is demoted to '## '. balance_fences (clean.py:87-111) then treats any '##'+ line while a fence is open (clean.py:105) as a forgotten-close and inserts a '```', splitting the block. balance_fences was explicitly designed to protect single-'#' shell comments (see its docstring and test_balance_fences_ignores_shell_comment, test_clean.py:51), but that protection is fully defeated because demotion converts '#' -> '##' first. Net downstream damage: commands leak out of code blocks (lose language/code metadata), and the comment text becomes real ATX headings = false HARD chunk boundaries in the ingestion parser.
- **Failure scenario:** Verified end-to-end: a clean, correctly-closed block
```bash
# Create the VLAN-backed network
nutanix@cvm$ acli net.create vlan0 vlan=0
# Verify it was created
nutanix@cvm$ acli net.list
```
After clean_document, markdown_it_parser produced 4 sections instead of 1, with bogus headings titled 'Create the VLAN-backed network' and 'Verify it was created' (the shell comments), and BOTH 'acli net.create'/'acli net.list' were NO LONGER captured as code (has_code False / empty code_blocks). Commands demoted to prose; false chunk boundaries created.
- **Suggested fix:** Make demote_extra_h1s AND balance_fences track open ``` fences and skip any line inside a fence. demote_extra_h1s must not demote lines inside code; balance_fences must not treat in-fence '#'/'##' lines as headings. (A shared _iter_lines_with_fence_state helper.)

### 3. [HIGH] balance_fences closes a fence at any H2+ line, corrupting code blocks that legitimately contain '##' comments
- **Location:** `clean.py:105` · **Dimension:** extraction-quality · **Verdict:** confirmed
- **What:** Independently of demotion, balance_fences (clean.py:105) inserts a closing '```' the moment it sees an _H2PLUS_RE line ('## '..'###### ') while a fence is open. Its docstring claims only single-'#' is risky, but '##'/'###' comments are valid and common in bash, YAML, INI, Dockerfiles, and annotated config examples (the prompt explicitly fences 'config-file' content, prompts.py:80-90). Any such comment inside a legitimately-closed code block triggers a premature fence close: an empty/early-closed code block, the comment promoted to a heading, and the remaining code lines demoted to prose.
- **Failure scenario:** Verified: balance_fences('## Section\n\n```bash\n## configure interface\nip addr add 1.2.3.4/24 dev eth0\n```\n') mutates the input, closing the fence right after ```bash, promoting '## configure interface' to a heading and leaving 'ip addr add ...' as unfenced prose. The command loses code metadata and a spurious section boundary is injected downstream.
- **Suggested fix:** Only auto-close a fence at a heading if the fence is actually unbalanced across the whole document; better, make balance_fences fence-state aware so a '##' line encountered inside an already-open fence is treated as code content, not a heading (mirror the single-'#' exemption for all '#' counts inside fences).

### 4. [HIGH] _FURNITURE_BAND_RE deletes legitimate table rows whose last cell is a number
- **Location:** `stitch.py:19` · **Dimension:** extraction-quality · **Verdict:** confirmed
- **What:** _FURNITURE_BAND_RE = ^\s*\S.*\|.*\|\s*\d+\s*$ (stitch.py:19), applied at stitch.py:62 and stitch.py:72, is meant to catch footer bands like 'AHV | Host Network Management | 60'. But it also matches any borderless or partially-bordered GFM table row whose final cell is numeric. Sizing/config/limits tables in this corpus are full of number-terminated cells (counts, ports, RF values, node maxima), and VLM output does not always include a trailing outer pipe, so such rows are silently dropped as furniture.
- **Failure scenario:** Verified matches (dropped): 'Replication factor | Minimum | 2' (borderless) and '| Max nodes | Cluster | 32' (leading pipe, missing trailing pipe). Both are real data rows that get deleted. (Fully-bordered rows ending in '|' are safe, so the loss is silent and data-dependent.)
- **Suggested fix:** Anchor the furniture band to true page furniture: require the numeric tail to be a small page-number-like integer AND the line to NOT be a table row (reject if it starts or ends with '|', or contains a run of table-separator dashes elsewhere). Prefer matching the specific repeated band text detected by the frequency pass over a generic 'ends in a number' regex.

### 5. [HIGH] Manifest fast-path reuses cached sha256/page_count/abs-path on (rel_path, size) equality — a same-size content edit serves stale transcriptions
- **Location:** `manifest.py:192` · **Dimension:** resume-cache · **Verdict:** confirmed
- **What:** build() reuses a prior DocRecord verbatim whenever rel_path matches and byte size is unchanged: `if prev is not None and prev.size_bytes == pdf.stat().st_size: records.append(prev); continue` (manifest.py:190-194). No rehash, no mtime check. Because the reused record carries the OLD sha256, page artifacts — which are keyed by that sha (artifacts.py:45) — are all considered already done, so convert never re-rasterizes and assemble emits the OLD content. A PDF edited in place to a byte-identical size (in-place metadata/string edits, or re-exports that land on the same length) is therefore silently NOT re-converted. Second failure mode from the same over-trust: the reused record also keeps the cached ABSOLUTE pdf_path (scan_pdf sets pdf_path=str(pdf_path.resolve()), manifest.py:122), which convert feeds straight to the rasterizer (convert.py:110 -> job.pdf_path). If the corpus tree is relocated to a new absolute root but sizes are unchanged (e.g., the manifest.jsonl + work_dir are copied from /home/bgconley/... on the GPU box to /Users/... locally, which the described workflow does), every reused record points at a nonexistent path and rasterize fails on every page.
- **Failure scenario:** A Nutanix guide is corrected (a typo fix that keeps the file exactly the same byte length) and dropped back into input_dir under the same name. Re-running convert: build() sees matching rel_path and identical size -> reuses the old DocRecord (old sha). is_done() finds every page already ok under the old sha -> nothing re-converts. assemble reads the old page artifacts and writes the pre-correction transcription into the corpus. The edit never reaches the RAG system, with no warning.
- **Suggested fix:** Drop the size-only shortcut (hashing is negligible next to a VLM pass) or, at minimum, also require matching mtime, and always refresh the record's absolute pdf_path from the freshly discovered file even when reusing sha/page_count.

### 6. [HIGH] Empty / partial VLM response is persisted as a successful page, creating silent gaps that resume never repairs
- **Location:** `convert.py:189` · **Dimension:** robustness · **Verdict:** confirmed
- **What:** vlm_client.py:197 does `content = choice["message"].get("content") or ""`, so a null/empty content (content_filter, a refusal, or an engine that returns the answer in reasoning_content with null content — the module docstring acknowledges vLLM vs SGLang differ here) becomes an empty string. convert._process (convert.py:189-196) then calls artifacts.write_success with that empty markdown and increments `converted`. finish_reason is only inspected for "length" (truncation); "content_filter"/"stop"-with-empty are treated as success. Because the artifact is written status=ok, artifacts.is_done() returns True on a later run so the page is never re-attempted, and document_coverage still reports the doc complete, so output.assemble_document writes it with a hole.
- **Failure scenario:** The model returns empty content for one dense page (content filter, or SGLang emits reasoning_content with content=null). The page is cached as ok, the doc is marked complete and written to the RAG corpus missing that page's content, no failure/suspect is recorded, and re-running `convert`/`retry-failed` skips it because it looks done. Silent, permanent data loss.
- **Suggested fix:** In _process, treat empty/whitespace-only content (or finish_reason not in {stop,length}) as a retryable failure via _retry_or_fail rather than write_success; only persist ok when non-empty content was returned.

### 7. [HIGH] If write_failure raises inside the worker's except handler (e.g. disk full), the worker dies and queue.join() hangs forever
- **Location:** `convert.py:152` · **Dimension:** robustness · **Verdict:** confirmed
- **What:** _worker (convert.py:143-158) does queue.task_done() in finally, but the except-branch body itself calls artifacts.write_failure (convert.py:152), which does mkdir + two write_text calls. On a full/read-only filesystem those raise; the exception escapes the except block (after finally runs task_done), so the worker coroutine terminates. Remaining queued pages then have no worker to service them, and the earlier `await queue.join()` (convert.py:132) blocks on the still-positive unfinished-task count. The run hangs with no error and no progress rather than failing.
- **Failure scenario:** Disk fills partway through a 936-page run (many artifacts written). The next failing page's write_failure raises inside the handler, killing that worker; as more workers hit the same condition they all die, and the process hangs at queue.join() indefinitely instead of exiting with an error.
- **Suggested fix:** Wrap the except body (including write_failure) in its own try/except so a worker can never die, or make _worker's loop resilient and drain the queue on fatal I/O errors; consider cancelling the run explicitly on unrecoverable disk errors.

### 8. [HIGH] Two PDFs with the same filename stem produce the same slug and silently overwrite each other's output
- **Location:** `output.py:102` · **Dimension:** robustness · **Verdict:** confirmed
- **What:** slugify (manifest.py:71-78) derives the slug from the filename stem only, and output_path (output.py:43-47) maps slug -> dir/<slug>/<slug>.md (or flat dir/<slug>.md). discover() walks recursively (rglob), so identically named files in different product subdirectories collide. The manifest keys by sha256 so both docs are kept and both are assembled, but assemble_document's out.write_text (output.py:102) writes both to the same path — last writer wins, with no warning.
- **Failure scenario:** aos/release-notes.pdf and files/release-notes.pdf both slugify to 'release-notes'; both convert successfully, but only the second-assembled one survives on disk. The corpus silently drops a whole document with a success-looking run report.
- **Suggested fix:** Disambiguate output paths by rel_path (or a sha suffix) when slugs collide, or detect duplicate slugs and error/warn during assembly.

### 9. [HIGH] Truncated (and empty) model output is persisted as a successful page with no marker
- **Location:** `convert.py:181` · **Dimension:** tests-observability · **Verdict:** confirmed
- **What:** convert.py:181-193: a length-truncated response triggers exactly one max_tokens bump, then write_success is called UNCONDITIONALLY on the result. If the bumped retry also truncates (finish_reason='length' again), the truncated markdown is stored as a normal ok artifact — PageMeta (artifacts.py:26-40) has no `truncated` field, and the QA heuristics (empty/garbled/repetition) do not detect a cleanly-truncated page. Similarly vlm_client returns content = `... or ""` (vlm_client.py:197), so an empty model reply is written as an ok page; nothing retries it, only advisory QA notes it as 'empty'. Both paths are untested (the live smoke asserts non-empty, but it is network-gated).
- **Failure scenario:** A dense spec/CLI page needs >12000 output tokens; the bumped retry still hits the ceiling. The mid-table truncated markdown is written status=ok, coverage shows the doc 'complete', and it ships with a silently cut-off table — undetectable from the report.
- **Suggested fix:** Record finish_reason/truncated in PageMeta; count still-truncated-after-bump pages into the report and/or mark them suspect. Consider treating persistently-empty content as a failure rather than ok.

### 10. [MEDIUM] Disabling all endpoints (documented DOCPIPE_DISABLE=oxcart) crashes or hangs convert with no clear error
- **Location:** `cli.py:94` · **Dimension:** cli-config · **Verdict:** confirmed
- **What:** Blackbird is disabled by default, so disabling oxcart leaves zero active endpoints. config.py:144-148 documents exactly this (`DOCPIPE_DISABLE=oxcart`) and test_config.py:33-39 asserts `active_endpoints == []` is a valid reachable state, but the run path has no guard. In the default (no --model) path, `VLMPool.resolve_model_id` probes zero endpoints, gets `served={}`, and executes `next(iter(served.values()))` at vlm_client.py:135 -> StopIteration escapes the coroutine as a cryptic RuntimeError (cli.main only catches KeyboardInterrupt). If a model id IS supplied (--model / DOCPIPE_MODEL_ID / toml model_id), resolve short-circuits, Converter.run enqueues every page but spawns zero workers (convert.py:126-131 iterates the empty active_endpoints), and `await queue.join()` at convert.py:132 blocks forever because task_done() is never called -> permanent hang, escapable only by Ctrl-C.
- **Failure scenario:** `DOCPIPE_DISABLE=oxcart docpipe convert` (the inline-documented example) -> StopIteration/RuntimeError traceback. `DOCPIPE_DISABLE=oxcart docpipe convert --model qwen36-27b` -> infinite hang at queue.join() with N pages enqueued and no workers.
- **Suggested fix:** In _load_config (or _run_pipeline before VLMPool) raise SystemExit if `not cfg.active_endpoints`, with a message naming the disabled endpoints.

### 11. [MEDIUM] TOML [[endpoints]] wholesale-replaces the default list; a partial entry silently drops the other endpoint and resets bearer/inflight to field defaults
- **Location:** `config.py:156` · **Dimension:** cli-config · **Verdict:** confirmed
- **What:** _merge_toml (config.py:152-157) does a shallow `merged.update(data)`, so any `[[endpoints]]` array in docpipe.toml replaces the entire curated default list rather than merging by name. Unspecified fields then fall to EndpointConfig FIELD defaults (bearer=None, inflight=5, weight=1.0, enabled=True) which differ from the curated _default_endpoints values (oxcart bearer='EMPTY', inflight=6). The `if not cfg.endpoints` guard at config.py:182-183 does not help: base=model_dump() always injects the two default endpoints, so the list is non-empty and the guard only fires on an explicit `endpoints = []` (its 'TOML omitted -> keep defaults' comment is therefore wrong about the mechanism). Nested scalar tables ([rasterize]/[convert]/[output]) survive partial overrides only by accident, because their curated defaults happen to equal their field defaults; endpoints is the one sub-model where they diverge.
- **Failure scenario:** User edits docpipe.toml to change only oxcart's URL by writing a single `[[endpoints]]` block with name+base_url. Result: blackbird vanishes entirely, and oxcart loses bearer -> None. Oxcart (vLLM) requires `Authorization: Bearer EMPTY`, so every request now 401s; inflight also silently drops 6->5. DOCPIPE_OXCART_BEARER can't rescue it if the trimmed toml renamed/omitted 'oxcart'.
- **Suggested fix:** Deep-merge sub-tables and merge endpoints by name (overlay onto _default_endpoints), or document that [[endpoints]] must always be fully specified and re-inject curated defaults for known names.

### 12. [MEDIUM] status is PROMPT_VERSION-blind: reports fully-converted docs as all-missing after a prompt bump and prints duplicate rows
- **Location:** `artifacts.py:161` · **Dimension:** cli-config · **Verdict:** confirmed
- **What:** The page-artifact cache key is (sha, page, dpi, model, PROMPT_VERSION) -- _page_dir bakes PROMPT_VERSION into the directory (artifacts.py:45). But discover_keysets (artifacts.py:146-163) reads the sidecar JSON, which has no prompt_version field, and returns only (m.dpi, m.model_id). cmd_status then calls document_coverage(work, rec, dpi, model_id) (cli.py:141-142) which re-derives the path with the CURRENT PROMPT_VERSION. So keysets written under a different prompt version are looked up in the wrong directory.
- **Failure scenario:** A doc is fully converted at PROMPT_VERSION='2'; prompts.py is later bumped to '3'. `docpipe status` discovers keyset (200, model) from the p2 sidecars but document_coverage reads the (nonexistent) p3 dir -> every page 'missing' -> status shows 0 ok / 936 missing for a completed doc, likely triggering a needless full re-run. If both p2 and p3 dirs exist, discover_keysets emits two identical (200, model) tuples -> two duplicate rows, both showing the p3 numbers.
- **Suggested fix:** Include prompt_version in the keyset (store it in PageMeta and return it from discover_keysets), and have document_coverage accept/scan the actual on-disk keyset dir rather than re-deriving from the current PROMPT_VERSION.

### 13. [MEDIUM] A fast-failing endpoint monopolizes the shared queue and burns the global max_retries budget, permanently failing pages a healthy endpoint could have converted
- **Location:** `convert.py:201` · **Dimension:** concurrency · **Verdict:** confirmed
- **What:** Retries have no endpoint anti-affinity and `job.attempts` is a single GLOBAL counter (convert.py:200-201), while routing is 'any free worker grabs the next queue item' (`queue.get()` at convert.py:145). A re-enqueued job (convert.py:212 `await queue.put(job)`) is therefore just as likely to be picked up by the SAME broken endpoint that failed it. Worse, an endpoint that fails FAST (connection-refused / instant 5xx) cycles its workers through the queue far quicker than a healthy-but-slower endpoint completing real transcriptions, so the broken endpoint drains a disproportionate share of the queue and re-fails those pages. Because all 4 attempts can be consumed on the one bad endpoint, the page is written as a permanent failure (`_fail`, convert.py:202/214-221) and dropped from the assembled doc. The routing that is supposed to give 'least-outstanding-requests failover' actually rewards the fastest-failing host with the most work — a failure amplifier, the inverse of the documented behavior.
